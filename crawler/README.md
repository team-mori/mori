# 모리(Mori) 크롤러 모듈 설계 문서

> 이 문서는 모리 서비스의 **공지 데이터 수집(크롤러) 모듈**에 대한 설계 명세입니다.
> 사람과 AI 코딩 에이전트(Claude Code, Gemini CLI 등) 모두가 이 모듈의 맥락과 의도를
> 파악할 수 있도록 작성되었습니다. 코드 작업을 시작하기 전 이 문서를 먼저 읽으세요.

---

## 1. 프로젝트 배경

모리(Mori, "모두의 리마인더")는 대학 공지에 흩어진 일정 정보를 자동으로 수집·추출하여
개인 캘린더와 연동하는 웹 서비스입니다. 전체 서비스의 데이터 흐름은 다음과 같습니다.

```
공지 게시판 → [크롤러] → [일정 추출] → DB → API 서버 → 웹 대시보드 / Google Calendar
```

이 문서가 다루는 범위는 위 파이프라인의 **첫 단계인 크롤러 모듈**입니다.
크롤러는 국민대학교의 여러 공지 게시판에 접속해 공지를 수집하고, 본문에서
날짜 정보를 추출하여 구조화된 데이터(DTO)로 만드는 역할을 합니다.

### 담당자

크롤러 및 텍스트 파싱 모듈은 데이터 수집 담당 팀원이 개발합니다.
API 서버 및 DB는 백엔드 담당 팀원이 별도로 개발하며, 크롤러가 만든 결과물(DTO)을
넘겨받아 DB에 적재합니다.

## 2. 기술 스택

| 항목 | 선택 | 비고 |
|------|------|------|
| 언어 | Java | 백엔드와 언어 통일 |
| 빌드 도구 | Gradle | `build.gradle` 사용 |
| 크롤링 라이브러리 | Selenium | WebDriver 기반 브라우저 자동화 |
| 드라이버 관리 | Selenium Manager | Selenium 4 내장. 드라이버 수동 설치 불필요 |
| 테스트 | JUnit 5 | |

> **중요 — 폐기 대상 안내**
> 현재 팀 레포지토리(`main` 브랜치)에 존재하는 `backend/` 의 Python 크롤러,
> Supabase 마이그레이션, GitHub Actions cron은 **단기 데모(v1)용이며 폐기 대상**입니다.
> 본 문서가 정의하는 Java 기반 크롤러가 실제 개발 산출물입니다.
> Python 크롤러 코드를 참고하거나 재사용하지 마세요.

## 3. 디렉토리 구조

크롤러 모듈은 메인 서비스 레포지토리 루트의 `crawler/` 디렉토리에 위치합니다.

```
crawler/
├── build.gradle                  # 크롤러 전용 독립 빌드 설정 (셀레니움 의존성)
├── .env                          # 환경 변수 (반드시 .gitignore에 등록)
└── src/
    ├── main/
    │   └── java/
    │       └── com/mori/crawler/
    │           ├── config/        # 셀레니움 WebDriver 초기 설정
    │           ├── scraper/       # 게시판별 크롤링 로직 + MasterScraper
    │           ├── parser/        # 공지 본문에서 날짜 추출 (일정 추출 엔진)
    │           └── dto/           # 데이터 전송 객체 + ENUM
    └── test/
        └── java/
            └── com/mori/crawler/  # 크롤러 / 파서 테스트 코드
```

### 패키지 역할 요약

- **config/** — 크롬 브라우저 공통 설정. 헤드리스 모드, 대기 시간(wait) 등.
- **scraper/** — 게시판에 접속해 공지를 추출하는 핵심 로직. MasterScraper와
  게시판별 개별 스크래퍼가 모두 여기 위치합니다.
- **parser/** — 추출한 공지 본문 텍스트에서 신청 기간·마감일 등 날짜 정보를
  규칙 기반으로 분석·구조화합니다.
- **dto/** — 크롤링·파싱 결과를 담는 객체. 백엔드 API 서버로 넘기는 데이터 형식.

## 4. 스크래퍼 설계

### 4.1 MasterScraper — 크롤링 진입점

`MasterScraper`는 전체 크롤링 과정의 **진입점이자 중앙 제어 장치**입니다.
직접 게시판을 크롤링하지 않고, 개별 스크래퍼들을 호출·관리하는 역할만 합니다.

책임:

1. **개별 스크래퍼 실행** — 등록된 게시판별 스크래퍼(학사공지, 조형대학 공지,
   도서관 공지 등)를 모두 실행시킵니다.
2. **상태 모니터링** — 각 스크래퍼가 정상적으로 데이터를 수집했는지, 실행 중
   오류가 발생하지는 않았는지 결과를 추적·관리합니다.

확장성: 크롤링 대상 게시판이 늘어나도 MasterScraper에 새 스크래퍼를 등록하기만
하면 됩니다.

#### 실행 정책 (확정)

- **실행 방식**: **병렬 실행**. 게시판별 스크래퍼를 동시에 실행해 전체 수집
  시간을 줄입니다. 각 스크래퍼는 독립된 WebDriver 인스턴스를 사용하므로,
  병렬 실행 시 인스턴스가 서로 간섭하지 않도록 구현에 주의합니다.
- **부분 실패 처리**: 스크래퍼 하나가 실패해도 **나머지는 계속 실행**합니다.
  한 게시판의 장애가 전체 수집을 막아서는 안 됩니다. 실패한 스크래퍼는 상태
  기록에 남겨, MasterScraper가 어떤 게시판이 실패했는지 보고할 수 있도록 합니다.

#### 실패 감지 정책 (확정)

MasterScraper는 각 스크래퍼의 결과를 **SUCCESS / PARTIAL / FAILED** 세 등급으로
받아 종합한다.

| 등급 | 판정 기준 |
|------|-----------|
| `FAILED` | 실행 중 예외 발생, 또는 게시판 핵심 요소(목록 컨테이너 등)를 찾지 못함 |
| `PARTIAL` | 크롤링은 됐으나 일부 공지에서 필수 필드(제목·링크) 누락 등 부분적 문제 |
| `SUCCESS` | 정상 완료. **수집된 공지가 0개여도 SUCCESS에 포함** |

> **0개는 실패가 아니다.** 크롤러는 짧은 주기로 반복 실행되므로, 신규 공지가
> 없으면 수집 결과가 0개인 것이 정상이다. 따라서 결과 개수로 실패를 판단하지
> 않는다. 실패는 '결과의 양'이 아니라 '크롤링 과정'에서 감지한다.

MasterScraper는 실행 종료 후 등급별 집계(성공 N / 부분 M / 실패 K)와
실패한 게시판 및 사유를 리포트로 남긴다.

### 4.2 개별 스크래퍼

각 게시판마다 하나의 스크래퍼가 대응합니다. 예: 학사공지, 조형대학 공지,
도서관 공지 등. 개별 스크래퍼는 해당 게시판에 접속해 공지 목록을 순회하며,
각 공지를 `NoticeDto` 객체로 변환합니다.

모든 개별 스크래퍼는 **공통 인터페이스(`Scraper`)를 구현한다.** MasterScraper가
게시판별 사정을 모르고도 모든 스크래퍼를 동일하게 호출·실행할 수 있어야 하기
때문이다.

- 인터페이스는 "공지를 수집해 결과를 반환한다"는 단일 동작을 규격화한다.
- 반환값에는 수집된 `NoticeDto` 목록과 실행 등급(`SUCCESS` / `PARTIAL` /
  `FAILED`)이 함께 담긴다.
- 개별 스크래퍼는 크롤링을 단계로 나누고, **"목록 컨테이너를 찾지 못함(FAILED)"**
  과 **"컨테이너는 찾았으나 공지 행이 0개(SUCCESS)"** 를 반드시 구분해 등급을
  판정한다.

> 0개 행과 컨테이너 부재를 구분하는 것이 실패 감지의 핵심이므로, 셀렉터를
> **게시판 컨테이너용**과 **공지 행용**으로 분리해 작성할 것.

## 5. 데이터 모델 (DTO)

### 5.1 NoticeDto

크롤러가 공지 하나를 수집할 때마다 생성하는 데이터 전송 객체입니다.
**DB 테이블도 이 구조와 거의 동일하게 설계됩니다.**

| 필드 | 설명 | 비고 |
|------|------|------|
| `title` | 공지 제목 | |
| `link` | 공지 본문 URL | |
| `postDate` | 게시 날짜 | |
| `deadline` | 마감 날짜 | **없을 수 있음 → nullable** |
| `category` | 공지 종류 | `NoticeCategory` ENUM |

> 모리 서비스의 핵심 가치는 공지에서 "기한·마감 날짜"를 뽑아내는 것입니다.
> 따라서 `deadline` 추출은 크롤러의 가장 중요한 기능 중 하나입니다.
> 마감일이 명시되지 않은 공지도 많으므로 `deadline`은 반드시 nullable로 둡니다.

### 5.2 NoticeCategory ENUM

공지의 **종류**를 구분하기 위한 열거형입니다. 종류는 여러 가지가 있을 수 있으며, 아래 두 가지는 예시입니다.

1. **대학 공지** — 학사공지, 장학공지, 비교과, 학과공지 등
2. **사업단 공지** — LINC 3.0 사업단, 차세대통신사업단, 미래자동차사업단 등
   (사업단은 여러 개가 존재함)

> ENUM에 들어갈 구체적인 항목 목록은 실제 크롤링 대상 게시판이 확정되면
> 그에 맞춰 정리합니다. 위 항목들은 예시이며 **확정 전 검토 필요**입니다.

## 6. 보안 / 환경 변수

- API 키 등 민감 정보는 코드에 하드코딩하지 않고 `crawler/.env`로 관리합니다.
- `.env`는 반드시 레포지토리 루트의 `.gitignore`에 등록하여 GitHub에 노출되지
  않도록 합니다.
